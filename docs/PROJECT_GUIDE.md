## 1. What the project is

BehaviourIQ is a web app that shows how the **past behaviour of customers** can be used to **predict how they will respond to a promotion**, and then uses that prediction to make better promotion decisions.

The one-sentence version: *"Instead of giving the same discount to everyone, learn from what each customer has done before, predict who will respond to which promotion, and spend the discount budget only where it earns money."*

The app does the following, in this order:

1. Reads customer purchase history (one row per product in an order).
2. Measures behaviours for each customer: how often they shop, what they spend, what share of their purchases are on promotion, how loyal they are to our brand, how large their baskets are, when they shop, and so on.
3. Sorts customers into five **customer types** according to how they react to promotions.
4. Trains a prediction model that estimates each customer's chance of buying, **with** and **without** a given promotion.
5. Compares the two chances to estimate the promotion uplift (estimated from observed behaviour against each customer's own baseline; there is no randomised test or control group in the data), and turns that into expected revenue, margin, cost, profit and ROI.
6. Checks honestly whether this works, by testing on past campaigns the model never saw.
7. Recommends which customers to target with which promotion, lets managers simulate alternatives, and plans next quarter's campaigns.

## 2. The business setting and key assumptions

The demo is set in **retail**, for the retailer **Reliance Fresh**. The data looks like loyalty-card data from a grocery / FMCG store. It is **simulated demo data and not actual Reliance Fresh data**: no real figures, customers, margins or campaigns are implied.

* There are **six product categories**: Beverages, Snacks, Breakfast, Dairy, Household, Personal Care.
* In every category the products we are promoting are the retailer's own label, **Reliance Fresh** ("our brand"), and the competitors are other brands on the same shelf (fictional brands such as Fizzo, Crispo, GoldenGrain, DairyDale, Sparkle, Silkora). Reliance Fresh is not modelled as one store competing against other store chains; that would need cross-retailer data.
* Every promotion discounts **Reliance Fresh own-label products only**.
* **Profit** means the margin on Reliance Fresh products (list price minus unit cost) after the discount, so the party funding the discount (the retailer, or the retailer and brand together) is the one measuring ROI.

**Why retail-shaped?** Two of the five customer types need to see competitor purchases (a "switcher" moves from a competitor to us; a "buys anyway" customer is loyal to us). A brand manufacturer usually cannot see what customers buy from rival brands, but a retailer or a shopper panel can. So the data has to look like a retailer's.

This is an assumption made while building the demo, not something fixed by the task. The method itself does not depend on it: it only needs order history, prices, costs and promotion records.

**The data is simulated.** No real customers are involved. It was generated by a script so that customers behave in realistic, different ways. This means the results prove the **method** works; they do not prove it works on your real customers. See [section 15](#15-limitations-and-honest-caveats).

## 3. How to run it

```
npm install
npm run dev            # opens at http://localhost:5173
npm run build          # production build
npm run typecheck      # TypeScript check
npm run data:generate  # regenerate the demo CSV (seeded, so identical every time)
npm run check:engine   # run the whole analysis in Node and print key numbers
npm test               # engine invariant tests (node --test, no extra dependency)
```

* The app loads `public/data/promo_behaviour_data.csv` when it starts and runs all calculations **in the browser** (about 2 to 4 seconds on first load, while "Analysing customer behaviour..." is shown). There is no server and no database.
* **Load CSV** (bottom of the sidebar) lets you load another file with the same columns. All pages recalculate.
* Navigation uses the address hash (`#/analytics`, `#/customers`, `#/planning`, `#/simulation`, `#/advisor`).
* Decisions made on the Planning page (Accept / Reject) are stored in the browser's local storage under `behaviouriq.decisions`.

## 4. What was built, and how it evolved

### Starting point

The original app was a pizza-delivery demo. Its numbers came from random values drawn per segment, its "predictions" were hand-weighted formulas, and its customer segments did not match the five consumer types in the research brief. It had no promotion history, so it could not tell whether a promotion actually caused a sale or whether the customer would have bought anyway. It had no AI recommendations and no chatbot.

### What was rebuilt

| Area | What was done |
|---|---|
| **Data** | One single CSV, generated by a seeded script. Retail setting, 30 past campaigns, all five consumer types, channel and minimum-spend columns. |
| **Customer types** | The five research types (Buys anyways, Deal-only, Stock-up, Switcher, Ignores) are assigned from observed behaviour with plain, readable rules. |
| **Prediction** | A logistic regression estimates the chance of buying with and without a promotion. Asking twice gives the estimated uplift (chance with the promotion minus chance without). It is trained on earlier time and tested on later campaigns, so there is no cheating. |
| **Incrementality** | Every past campaign is measured against each customer's own normal buying, including the dip afterwards, so "would have bought anyway" is counted, not guessed. |
| **Economics** | Revenue, margin, discount cost, wasted discount (leakage), stock borrowed from later weeks, profit and ROI for any customer and any promotion. |
| **Validation** | A backtest on 8 held-out campaigns answers: is the prediction accurate, and does acting on it make or lose money. |
| **Planning** | Six upcoming campaigns are scored against six promotion types; the best option, audience, budget, confidence and warnings are produced. |
| **Simulation** | A what-if tool with objectives, budget cap, ROI guardrail and audience filter, compared with the AI recommendation. |
| **Chatbot** | A local question-answering assistant that reads the same numbers (no outside AI service). |

### How the interface evolved

The interface went through several rounds of feedback:

1. A first version was rebuilt in a light, card-based style.
2. It was then restyled to follow the reference screenshots (dark navy sidebar, filter bar, KPI cards with change chips, tables with Accept / Reject / Modify).
3. A ten-step "story" version was tried and **removed**, because only 3 to 4 pages were wanted.
4. The app was reduced to four pages, then a fifth (Customer Prediction) was added for customer-level detail.
5. Later rounds added more filters, replaced stage labels with plain section names, renamed the product **BehaviourIQ**, added chart / table switches, added a short always-visible key to every chart, and cut clutter by showing one section at a time on the main page.
6. Two similar-looking groupings (a spend-based one and the promotion-reaction one) caused confusion, so the spend-based one was removed from the interface. **One grouping remains: customer type.**

7. **Simplification round (tried, then reverted).** A restructure was tried that put Customer Prediction first, cut Behaviour Analytics down to three sections and added a validation banner. It was judged harder to read than the earlier layout, so the earlier layout (four tabs on Behaviour Analytics, Analytics first in the navigation) was restored. What was kept from that round: the single "Customer Type" term, "estimated" wording for uplift and incrementality with a caveat, a "Prediction vs decision" note in Simulation, and the automated tests.

## 5. The data

### 5.1 The file

`public/data/promo_behaviour_data.csv`, about 4.7 MB. **One row = one product line in one order.**

| Column | Meaning |
|---|---|
| `order_id` | Order number. Several rows share one order (that is the basket). |
| `customer_id` | Customer (C0001 to C0520). |
| `order_date` | Date of the order. |
| `product_id`, `product_name` | The product bought. |
| `category` | One of six categories. |
| `brand` | Reliance Fresh or a competitor brand. |
| `is_our_brand` | 1 for Reliance Fresh, 0 for competitors. |
| `quantity` | Units bought. |
| `list_price` | Normal price per unit. |
| `unit_price` | Price actually paid per unit (lower when discounted). |
| `discount_pct` | Percent discount applied on this line (0 if none). |
| `promo_id`, `promo_name`, `promo_mechanic` | The promotion this line was part of (blank if none). Mechanics are `PCT_OFF`, `FLAT_OFF`, `BOGO`, `MULTIBUY_3FOR2`. |
| `unit_cost` | What the product costs us per unit (used for margin). |
| `channel` | Store, App or Online. |
| `min_spend` | For flat ₹-off promotions, the minimum spend needed to get the discount. |

The first 16 columns are required. `channel` and `min_spend` are optional.

### 5.2 Size

In this build: **520 customers, 22,798 orders, 48,213 order lines, about ₹99 lakh of revenue**, from **1 July 2025 to 30 September 2026** (15 months), with **30 past campaigns**.

### 5.3 The product catalogue

24 products, 4 per category: two Reliance Fresh own-label products and two competitor products. For example Beverages has Reliance Fresh Cola, Reliance Fresh Iced Tea, Fizzo Cola and Zing Energy Drink. Prices range from about ₹38 to ₹320, with a margin of roughly 20% to 45% depending on the product.

### 5.4 The 30 past campaigns

Every campaign lasts 14 days and is one of **five promotion types** (plus "no promotion" as the baseline):

| Type | How it works in the data |
|---|---|
| **10% Discount** | Percentage off Reliance Fresh products in the category (7 campaigns). |
| **20% Discount** | Same at 20% (9 campaigns). |
| **₹x Off on ₹y+** | A flat rupee amount off per unit, only when the customer spends at least ₹y on the line (5 campaigns). For example ₹30 off on ₹250+ in Household. |
| **BOGO** | Buy one get one free (6 campaigns). Quantity is forced to even numbers, minimum 2. |
| **Bundle / Combo Offer** | 3 for 2 (3 campaigns). Quantity in multiples of 3. |

Each category has 5 campaigns spread across the 15 months, and **every category has campaigns in the last 3 months**, so every filter has something to show. Campaigns include festival-linked ones (Diwali, Holi, Independence Sale) and seasonal ones (Summer Sip, Monsoon Dairy).

### 5.5 How the simulated customers behave

The generator creates each customer with a hidden behaviour type and then simulates day-by-day shopping:

* Each customer has a **shopping rate** (1 to 4+ trips a month), a **weekend preference**, **category preferences**, a **household quantity habit**, and a start and end date (some join late, some lapse).
* Each trip picks 1 to 4 categories, with realistic **pairs** (Snacks with Beverages, Breakfast with Dairy, Household with Personal Care).
* Within a category the customer chooses Reliance Fresh or a competitor with a probability that depends on their type.
* Some customers make **dedicated promotion trips** during a campaign, with a probability that rises with the discount depth.
* Seasonality is built in (beverages peak in summer, household peaks before Diwali, snacks peak in the festive months).

The five hidden types, and what they do:

| Type | Behaviour |
|---|---|
| **Buys anyways** | Mostly buys Reliance Fresh at full price whether or not there is a promotion. A discount only gives margin away. |
| **Deal-only** | Rarely buys Reliance Fresh at full price; responds strongly to almost every promotion, even shallow ones. |
| **Stock-up** | Buys 2.6 to 4 times the usual quantity on promotion, then holds off for weeks (pulling future purchases forward). |
| **Switcher** | Normally buys a competitor; tries Reliance Fresh only when the discount is deep (around 20% or more). |
| **Ignores** | Rarely buys Reliance Fresh and barely reacts to promotions. |

About 8% of customers are **hybrids** (a blend of two types) and about 17% join late or lapse, so the types overlap a little, as they do in real life.

The channel is assigned by a hash of the customer id and order id (so it does not disturb the random simulation): each customer has a preferred channel (Store 45%, App 35%, Online 20%) used for about 80% of their orders.

**Important:** the hidden type of each customer is saved only in `scripts/out/ground_truth.json`, for testing the classifier. It is never part of the CSV and the app never reads it.

## 6. The analysis engine, step by step

All logic lives in `src/engine/`. It runs in the browser. This section walks through it in the order the data flows.

### 6.1 Reading the file (`data.ts`)

* Parses the CSV into order lines and sorts by date. Dates are stored as day numbers.
* Groups lines by customer (sorted by date) for fast lookups.
* **Detects campaigns** from the `promo_id` column: each campaign's start and end are the first and last day a promoted line appears; depth is the largest discount seen; for flat offers it also records the rupee amount off and the minimum spend (and converts the amount to an **equivalent percentage** so it can be compared with percentage offers).
* Works out the **economics of our brand per category**: average list price and unit cost (weighted by units).
* Works out a **prior buying rate** per category: Reliance Fresh units per customer per day outside any promotion window. This is used to steady estimates for customers with little history.

### 6.2 The behaviour profile (`behaviour.ts`)

For one customer, using only orders **before a chosen date**, it measures:

| Group | Signals |
|---|---|
| **Purchasing** | orders, order lines, days since last order (**recency**), orders per month (**frequency**), average units per line, items per order, average order value, total spend. |
| **Price** | average discount % taken on promoted Reliance Fresh lines, lowest discount taken, share of Reliance Fresh lines bought at full price. |
| **Brand** | Reliance Fresh lines, competitor lines, **our-brand share at full price** (full-price Reliance Fresh lines divided by full-price Reliance Fresh plus competitor lines), **promo reliance** (share of Reliance Fresh lines bought on promotion), competitor items per month. |
| **Promotion** | **active campaigns** (ones the customer could have responded to), **responded campaigns** (bought a promoted Reliance Fresh item in the window), **response rate**, **lift** (units in promotion windows compared with their baseline), **quantity ratio** (units per promoted line divided by units per normal line, counting only percentage and flat offers), **dip ratio** (category buying in the 3 weeks after a promotion compared with normal). |
| **Timing** | weekend share of order days, average gap between orders (days), how regular the gaps are, share of orders in the Oct–Nov festive weeks. |
| **Basket / product** | share of lines in each category, top category and its share. |
| **Channel** | share of orders in each channel, preferred channel. |

Because every measurement uses only data before a date, the same function can build the model's training inputs without leaking the future.

**"Active" customers.** A customer counts as active for a campaign if they had an order in the 90 days before it started (or were new). The same 90-day rule is used for the "recently active customers" shown on the planning and prediction pages.

**Baseline buying rate.** `baselineRate()` estimates how many Reliance Fresh units per day a customer normally buys in a category: it looks back 120 days from the campaign start, ignores days inside any campaign window of that category (plus a 21-day tail after each), counts their Reliance Fresh units on the remaining days, and steadies the estimate towards the category average with a weight of 30 days:

```
baseline = (their units + 30 × category average) / (eligible days + 30)
```

This baseline is the foundation of "would they have bought anyway?".

### 6.3 The five customer types (`segments.ts`)

Types are assigned by **plain rules in this order**; the first rule that fits wins:

| Order | Rule | Type |
|---|---|---|
| 1 | Buys at least **1.7 times** the usual quantity when a percentage promotion runs | **Stock-up** |
| 2 | At least **55%** of their full-price purchases in our categories are Reliance Fresh | **Buys anyways** |
| 3 | Responded to fewer than **20%** of campaigns they could have | **Ignores** |
| 4 | Response rate below **55%** | **Switcher** |
| 5 | Everything else (response rate 55% or more) | **Deal-only** |

Each customer also gets a **confidence** (50% to 99%) showing how far they sit from the rule thresholds, and plain-language **reasons** (for example "Buys 3.2x the usual quantity when a promotion runs").

**Accuracy check.** Because the hidden true type is known only to the generator, the rules were tested against it: they match **about 92%** of customers. (This is a test of the rules on simulated data; it cannot be measured on real data without labels.)

The five types, in plain English:

* **Buys anyways**: would have paid full price. Discounts are wasted on them.
* **Deal-only**: buys when it is discounted. The core audience for percentage offers.
* **Stock-up**: buys extra on a deal, then buys less later. Looks great in the promotion window, less so afterwards.
* **Switcher**: normally buys a competitor; a deep offer gets them to try us, but they often drift back.
* **Ignores**: promotions do not move them. Spending budget here loses money.

> **Note on the hidden spend-based grouping.** The engine also has a second grouping (`groups.ts`: Loyal, High-Value, New, At-Risk, Occasional, based on spend, frequency and recency). It was **removed from the interface** because two groupings confused users. The code remains in case it is wanted again.

### 6.4 What did each past campaign deliver (`campaigns.ts`)

For every campaign and every active customer, the engine compares what happened with what would have happened:

* **A** = Reliance Fresh units the customer bought in that category during the 14-day window.
* **B** = their baseline for those 14 days (baseline rate × 14).
* **Incremental units** = A − B (can be negative).
* **Leakage share** = min(A, B) / A: the part of their purchases that would have happened anyway.
* **Discount cost** = (list price − price paid) × units, on those units.
* **Leakage (₹)** = discount cost × leakage share: discount handed to sales that would have happened anyway.
* **Post-promotion dip** = their baseline for the next 21 days minus what they actually bought in those 21 days (only when 21 days of later data exist).
* **Net profit** = margin earned in the window − margin they would have earned anyway (B × full-price margin) − margin lost in the dip (dip × full-price margin).
* **ROI** = net profit ÷ discount cost.
* **Verdict**: ROI of 0.5 or more is **Scale**, 0 to 0.5 is **Optimise**, below 0 is **Stop**.

This is the key idea behind "net profit" everywhere in the app: a promotion is only credited with what it **caused**, and it is charged for the discount given to people who would have bought anyway and for the buying pulled forward from later weeks.

Results are stored per customer per campaign, so any filter (customer type, channel, loyalty, frequency) can re-add them.

### 6.5 The prediction model (`model.ts`)

**The question it answers:** *"If customer X is offered promotion P in category C, what is the chance they buy our brand in the next 14 days?"*

**Type of model:** logistic regression (a standard, explainable method), trained in the browser with the Adam optimiser (450 steps, learning rate 0.05, light L2 regularisation), on standardised inputs.

**Training examples (about 19,800 in total):**

* **Campaign windows**: for every campaign, every active customer. Inputs are measured at the campaign start; the answer is "did they buy any Reliance Fresh item in that category during the window?".
* **Non-campaign windows**: 14-day slots with no campaign in that category (and none in the 21 days before), with the discount set to zero. The category rotates so all six are represented.

Including the no-promotion windows is what lets the model learn "what they do anyway".

**Honest testing:** the model is trained only on windows before the last **8 campaigns** (with a 14-day gap) and tested on windows after. The final model used for planning is then refitted on everything.

**The 19 inputs, by behaviour group:**

| Group | Inputs |
|---|---|
| Purchasing | days since last order, orders per month, own baseline buying of our brand in the category, promo-quantity-vs-normal-quantity |
| Price | average discount taken so far, discount depth offered, discount × promo reliance |
| Promotion | share of purchases made on promo, response to previous promotions, past volume lift, discount × past response |
| Brand | our-brand share in the category, competitor share of purchases, discount × competitor share, discount × our-brand share |
| Basket | share of basket in this category, items per order, multi-buy offer × stock-up tendency |
| Timing | days since last order compared with the usual interval |

The "discount ×" items let the model learn that **different behaviours react differently to a deeper discount**.

**Asking it twice.** The same model is evaluated at the offered depth and at zero depth:

```
chance with promotion    p1 = model(customer, depth d)
chance without promotion p0 = model(customer, depth 0)
uplift (lift)            = p1 − p0
```

**Quality on unseen campaigns (this build):**

| Measure | Value |
|---|---|
| AUC on the test period | **0.82** (training 0.80). 0.5 is guessing, 1.0 is perfect. |
| Share of all buyers inside the model's top 20% | **38%** |
| Average chance of buying in a 14-day window (test) | about 41% |
| Calibration (5 equal groups, predicted vs actual) | 77%/76%, 54%/62%, 40%/40%, 26%/21%, 10%/4% |

The calibration pairs show that probabilities are broadly honest, slightly cautious in the middle and slightly optimistic for the least likely group.

**What drives the prediction (share of the model's weight):**

| Behaviour group | Share |
|---|---|
| Brand (loyalty vs competitors) | about 42% |
| Promotion (past response and lift) | about 30% |
| Price | about 10% |
| Purchasing | about 10% |
| Basket | about 7% |
| Timing | about 1% |

### 6.6 Turning chances into money (`economics.ts`)

For a customer and an offer (category, depth, mechanic, minimum spend), `expect()` calculates:

* **Units if offered** = p1 × the customer's typical promotion quantity (at least 2 for BOGO, 3 for a bundle, and enough units to meet the minimum spend for a flat offer).
* **Units anyway** = p0 × their normal full-price quantity.
* **Revenue** = units × list price × (1 − depth).
* **Discount cost** = units × list price × depth.
* **Leakage** = min(units offered, units anyway) × list price × depth.
* **Profit with the offer** = units × (discounted price − cost).
* **Profit anyway** = units anyway × full-price margin.
* **Stock borrowed from later weeks** = the smaller of (extra units bought on promotion) and (what they would have bought in the next 21 days) × p1 × margin. Only the part of the extra units that could really have been bought in the next three weeks is counted, so the penalty is not overdone.
* **Net profit** = profit with the offer − profit anyway − stock borrowed.

### 6.7 The six promotion types (`options.ts`)

| Option | Depth used | Notes |
|---|---|---|
| **No Promotion** | 0 | The baseline: what customers do anyway. |
| **10% Discount** | 10 | |
| **20% Discount** | 20 | |
| **₹x Off on ₹y+** | equivalent % | x and y are taken from that category's own flat campaign in history (for example ₹10 off on ₹100+ in Beverages, ₹30 off on ₹300+ in Breakfast). |
| **BOGO** | 50 | Minimum 2 units. |
| **Bundle / Combo Offer** | 33 | 3 for 2, minimum 3 units. |

### 6.8 Who is worth an offer (the targeting rule)

A customer is worth offering a promotion only if **both** are true:

1. Expected **net profit is positive** (the offer earns more than it costs, after stock borrowed).
2. The offer raises their chance of buying by **at least 3 percentage points** (`MIN_LIFT`). This stops the model from chasing tiny gains that are really just noise.

This rule is used everywhere: planning, the target list, the best promotion per customer, the simulator's "maximise profit" objective, and the backtest.

### 6.9 Choosing the best promotion (`options.ts`, `recommendOption`)

The best promotion is **not** simply the one with the highest response. Each option is scored, among the audience it would be offered to:

```
score = 40% profit + 25% ROI + 20% incremental revenue + 15% response   (each scaled 0 to 1)
```

Options that lose money are ruled out, and options that would reach almost nobody (fewer than 10 customers or 5% of the base) are ignored. This is why the app can say "BOGO has the highest response, but 10% Discount is the better decision".

### 6.10 The planner and the alerts (`planner.ts`)

**Six upcoming campaigns** (the calendar is an input in `CANDIDATES`, not part of the CSV):

| Campaign | Category | Starts | Theme |
|---|---|---|---|
| Festive Clean-Up | Household | 12 Oct 2026 | Pre-Diwali cleaning peak |
| Diwali Beverage Fest | Beverages | 26 Oct 2026 | Diwali (8 Nov) |
| Diwali Snack Box | Snacks | 30 Oct 2026 | Gifting and guests |
| Winter Warm-Up Breakfast | Breakfast | 16 Nov 2026 | Cold-season breakfast |
| Dairy Winter Fest | Dairy | 23 Nov 2026 | Winter dairy demand |
| Year-End Glow | Personal Care | 14 Dec 2026 | Party season |

For each campaign the planner scores all five promotions across every recently active customer and picks the one with the highest total net profit among those with positive profit and at least 20 customers. For each it also stores a **blanket** result (what happens if the same offer goes to everyone), used to measure the value of targeting.

**Flags ("Needs attention").** A campaign is flagged when the expected ROI is below 0.65, or net profit is below ₹2,500, or the category has fewer than 2 earlier campaigns, or no promotion earns money.

**Confidence.** Not a made-up number. It is built from how well the model actually did in tests:

```
confidence = 45% + 30% × (AUC − 0.5)/0.5 + 22% × (share of backtest campaigns in this category that made money)
             (kept between 40% and 97%)
```

If a category has no backtest campaign, the overall share is used.

**Objective chip** ("Convert deal seekers", "Win competitor buyers", "Grow basket size", "Reward loyal buyers", "Re-engage non-responders"): derived from whichever customer type is most over-represented in the chosen audience compared with the whole base.

**Watchdog alerts** (shown on the Planning page):

* how many past promotions lost money, and the worst one;
* campaigns where more than 15% of the discount leaked to would-have-bought-anyway sales;
* how many customers buy regardless of promotions;
* Deal-only response fading (response in the last 3 campaigns at least 8 points below the first 3);
* stock-up customers borrowing from future sales (units missing in the 3 weeks afterwards);
* competitor customers who tried us but did not come back at full price within 30 days;
* regular customers (8+ orders) who have gone quiet for 45+ days.

### 6.11 The honest test (`campaigns.ts`, `validationByCampaign`, `backtest`)

For each of the **8 held-out campaigns** (the most recent: Monsoon Care, Glow Up, Monsoon Munch, Independence Sale, Back-to-School Breakfast, Cheese Carnival, Back-to-Work Fizz, Snack Festival):

1. The model fitted **only on earlier data** predicts every active customer's profit from that campaign's offer.
2. It contacts the customers that pass the targeting rule (positive profit and lift of at least 3 points).
3. The **actual** results of those customers are read from the real data and compared with what was predicted, with offering everyone, and with the customers it skipped.

The assumption: customers not contacted behave exactly as they normally do (no discount, no lift).

**Results in this build:**

| Strategy | ROI | Net profit | Discount spent |
|---|---|---|---|
| Discount everyone | 0.08 | ₹17.7K | ₹2.20 lakh |
| Skip Buys-anyways and Ignores (a simple rule by type) | 0.13 | ₹23.9K | — |
| Target the likely buyers (top half by chance of buying) | 0.13 | ₹22.9K | — |
| **Target by the model (positive profit and lift)** | **1.18** | **₹41.1K** | **₹34.9K** |

Other findings:

* The model **expected ₹17.1K** from the customers it picked; they **delivered ₹41.1K**. It is cautious, not over-confident.
* Customers it chose **not** to contact would have produced a **loss of ₹23.4K** if offered.
* In two campaigns (Monsoon Care BOGO and Back-to-School Breakfast bundle) the model chose to contact nobody; offering everyone would have lost ₹24.0K and ₹2.8K respectively.

### 6.12 The summary numbers that feed the pages (`index.ts`, `insights.ts`)

`buildEngine()` runs everything in sequence and returns one object used by all pages: the dataset, customer records (profile, type, confidence, reasons), model, campaign results, per-customer results, strategy and validation results, recommendations, alerts, and totals. It also records four "pipeline stages" with timings: Behaviour Analyst, Response Predictor, Campaign Planner and Watchdog. *(These stage logs are produced but are not displayed in the current interface.)*

`insights.ts` holds some extra calculations (response by discount depth, price ladder, brand switching, basket pairs, seasonality, monthly trend). Some are computed but not currently shown; they are available if new charts are wanted.

### 6.13 The chatbot brain (`advisor.ts`)

A set of rules that recognise the **intent** of a question (and things like customer IDs, categories, customer types and money amounts), then build an answer from the engine's numbers. No outside AI service is used and nothing leaves the browser. The recognised intents:

| Topic | Examples it understands |
|---|---|
| A specific customer | "tell me about C42" → type, why, and best next offer. |
| Best offer for a budget or category | "Best offer for ₹10K", "What should we run for Beverages?" |
| Accuracy and profit | "Is it accurate and does it make money?", "Which behaviours predict response?" |
| Waste | "Where are we wasting discount money?" |
| A customer type | "Who are the stock-up buyers?" |
| Overview of types | "What types of customers are there?" |
| Past campaigns | "Best campaign", "ROI" |
| Basket | "What do customers buy together?" |
| Timing | "When do people shop?" |
| Price | "How much discount?" |
| Brand | "Do competitor customers stay?" |
| Targeting | "Who should we target?" |
| Summary | "How are we doing?" |

Anything else gets a polite reply with suggested questions.

### 6.14 Prediction versus decision, and what "uplift" means

Two separate questions run through the whole app:

| Question | Answered by | Where |
|---|---|---|
| **Prediction:** will this customer respond? | The model's predicted response: chance of buying with a promotion (P1) and without it (P0) | Customer Prediction (chance with and without), Behaviour Analytics → Prediction |
| **Decision:** is it financially worth offering? | Economics: margin, discount cost, leakage, pull-forward, profit, ROI | Net profit and ROI columns, Target list, Planning, Simulation |

The highest predicted response is often **not** the most profitable offer (BOGO and Bundle raise response most but frequently lose money). That is why the app ranks by expected profit, not by response.

**Uplift** is P1 minus P0, in percentage points. It is an **estimate**: it comes from a model trained on observed behaviour and compared with each customer's own baseline. The data has no randomised test and control group, so uplift and "incremental" figures are estimated promotion effects, not measured causal effects. The held-out backtest (6.11) is the check that acting on the estimates still pays off.

## 15. Limitations and honest caveats

1. **The data is simulated.** The results show the method works, not that it works on your customers. Say so early; run it on real data to confirm.
2. **It assumes a retailer promoting one brand** (section 2). A brand manufacturer would need retailer or panel data.
3. **The model is a simple logistic regression.** It is explainable and quick, but not state of the art. It treats the effect of each behaviour as additive (plus the "discount ×" combinations).
4. **Profit relies on an assumption**: customers who are not contacted are assumed to behave as they normally do.
5. **Baselines are estimates.** "Would have bought anyway" comes from each customer's own history over the previous 120 days; customers with little history lean on the category average.
6. **Timing and channel add almost nothing** to the prediction here (timing about 1%). Channel is shown but is not used by the model.
7. **The prediction horizon is 14 days.** Per-customer profit figures (for example ₹49) are for that window, not annual value.
8. **Some groups are small** (for example, a few customers per type in a narrow filter), so percentages can swing.
9. **Flat ₹-off offers are modelled like the equivalent percentage discount**, with a quantity needed to reach the minimum spend.
10. **Some features are placeholders or hidden.** "Apply Simulated" does not save; the four engine pipeline stage logs are not displayed; the value-segment grouping exists in code but is not shown.
11. **The chatbot is rule-based.** It only understands the question types listed in 6.13.
12. **Uplift is estimated, not randomised.** There is no control group in the data, so promotion uplift and incrementality are estimates from observed behaviour against each customer's own baseline (see 6.14).
13. **The customer-type rules matching the hidden truth about 92% of the time** is a property of the simulated data, because the truth comes from the generator. It is not a result to quote as real-world accuracy.

## 17. Glossary

| Term | Meaning |
|---|---|
| **Our brand (Reliance Fresh)** | The Reliance Fresh own-label products being promoted. Competitors are other brands on the same shelf. |
| **Behaviour profile** | The set of measured behaviours for one customer. |
| **Customer type** | One of five groups by how customers react to promotions. |
| **Response / response rate** | Buying a promoted item during a campaign. Rate = share of reached customers who did. |
| **Baseline** | What a customer normally buys at full price, from their own history. |
| **Estimated incremental response** | Units or profit the promotion caused, above the baseline. |
| **Leakage** | Discount given on purchases that would have happened anyway. |
| **Pull-forward / dip** | Buying brought forward from later weeks, so later weeks are lower. |
| **Uplift / lift** | Chance of buying with the promotion minus the chance without it. |
| **AUC** | How well the model ranks customers: 0.5 is guessing, 1.0 is perfect. |
| **ROI** | Net profit divided by discount invested. |
| **Net profit** | Margin on promoted sales, minus margin that would have been earned anyway, minus the post-promotion dip. |
| **Backtest / held-out campaigns** | Testing the model on campaigns it did not see during training. |
| **Guardrail** | A limit (for example minimum ROI) the simulator checks. |
| **Traditional approach** | The same broad offer (here 20% Discount) to every recently active customer. |
| **Behaviour-based approach** | The best promotion, only for customers it pays off with. |

## 18. Suggested demo flow

About 10 minutes:

0. **Problem statement** (30 sec): "Can past customer behaviour predict who will respond to which promotion, and is it financially worth offering?" Say once that the data is simulated.
1. **Open Behaviour Analytics** (1 min): "Here is what promotions have done so far." Point at the six cards; note the net profit and ROI.
2. **Past results** (1.5 min): bubble chart (some campaigns lose money), incrementality (a lot of sales would have happened anyway), promotion types (BOGO and bundles lose).
3. **Customer behaviour** (1.5 min): the five types and the ROI view (some types cost money); the response map.
4. **Customer Prediction** (1.5 min): open one customer, show features, the six promotions, the recommendation and the "why". Point out that the promotion with the highest response is not always the most profitable (prediction versus decision, 6.14). Switch to Target list and export.
5. **Customer Prediction, model section** (3 min): open "How the model predicts, and does it work"; which behaviours predict (brand and promotion history); who responds to what; then the validation panel: accuracy view, then the profit view, then "what the model avoided".
6. **Planning and Simulation** (1.5 min): accept a campaign; in Simulation raise the discount and show the guardrail banner, the profit peak and the "Prediction vs decision" note.
7. **Business impact** (1 min, end of the Simulation page): traditional versus behaviour-based.
8. **AI Advisor** (30 sec): ask "Is the prediction accurate and does it make money?"

**Closing line:** *"Customer behaviour is not only useful for understanding what Reliance Fresh customers have done in the past. It can also help predict what promotions they are most likely to respond to in the future, and we tested that on campaigns the model had never seen."*

If asked about real data: *"This is a simulated dataset to demonstrate the method. The pipeline works the same on real data, and we can load your file with the same columns."*

## Appendix: customer-type classification accuracy

The rule-based Customer Types match the hidden simulation truth about 92% of the time. This is a property of the simulated data (the truth comes from the generator, which is never shipped with the app), so it is not shown as a headline result. The headline validation is the held-out backtest: behaviour-based targeting vs blanket promotion on campaigns not used for model training, plus the model's AUC. Promotion uplift figures throughout are estimates from observed behaviour against each customer's own baseline, not a randomised test.
